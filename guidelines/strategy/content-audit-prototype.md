# Prototype Content Audit

## Access note

This audit defines the required checks and the likely deltas to validate against the current Figma Make prototype codebase.

## Required checks against the prototype

### Information architecture coherence
Does the prototype move from "services list" to "systems outcomes" (tokens, patterns, governance, performance, AI visibility)?

### Authority sequencing
Are proof blocks placed before persuasion blocks (credibility first), and are they tied to measurable outcomes?

### Conversion architecture
Does the prototype include a mid-funnel conversion path (audit request) before the high-commitment consultation CTA?

### AEO formatting
Does the prototype format definitional content with scannable headings, short paragraphs, and "answer-first" patterns suitable for AI features?

## Anticipated strengths if built from a WordPress-aligned pattern system

If the prototype is driven by WordPress-aligned blocks/patterns and token usage, it can create a directly implementable design-to-theme mapping without "design drift."

## Anticipated risks to validate

### Pattern sprawl
Too many bespoke sections can undermine governance and make WordPress implementation brittle.

### Over-interaction
Excess JavaScript interactions can threaten INP and CWV targets; interactivity should follow progressive patterns and Interactivity API conventions when WordPress-native behaviour is desired.
